# OverlaySpike —— 鸣潮游戏内浮窗 Phase 0 原型

这个工程**不是**功能代码，是一次性实验器材。它存在的唯一目的是用实机事实回答四个问题，
避免在错误的技术路线上投入正式开发（背景见 `docs/wuwa-overlay-mod-switcher-prd.md` 的 Phase 0）。

**刻意不加入 `src/GIMI-ModManager.sln`**：不进 CI、不进 `dotnet format` 门禁，验证完整目录删掉即可。

---

## 要回答的四个问题

| #   | 问题                       | 为什么它决定生死                                            |
| --- | ------------------------ | --------------------------------------------------- |
| 1   | 独占全屏下，这扇窗能不能看见？          | 看不见的话「独立置顶小窗」方案直接作废，只剩注入式（工作量高一个数量级）                |
| 2   | 游戏锁定鼠标时，能不能点中它？          | 鸣潮是 TPS，3D 视角下鼠标被游戏捕获（`SetCapture`），浮窗可能**根本收不到点击** |
| 3   | 点击它时，游戏会不会掉全屏 / 最小化？     | 掉全屏就比 Alt+Tab 还糟，等于功能没有意义                           |
| 4   | 热键在**以管理员运行**的游戏前台时还有效吗？ | 鸣潮是 `require_admin = true`。若无效，「唤出浮窗」这件事本身就不成立      |

## 编译与运行

```powershell
# 先关掉正在运行的 JASM，避免输出目录被锁（见 CLAUDE.md 的常见坑）
dotnet build src/OverlaySpike/OverlaySpike.csproj -p:Platform=x64

# 产物
src/OverlaySpike/bin/x64/Debug/net9.0-windows10.0.22621.0/OverlaySpike.exe
```

运行 `OverlaySpike.exe` 即可，不需要管理员权限 —— **故意**如此：要验证的正是"非提权程序能不能把窗口盖在提权游戏上"。

> 如果 `-p:Platform=x64` 报找不到平台，改成 `dotnet build src/OverlaySpike/OverlaySpike.csproj` 直接试。

## 已经在开发机上预先验证掉的（**不用**你在游戏里重测）

这些是用外部探针程序读窗口真实状态得出的结论，不是"代码里调了 API 所以应该没问题"：

| 结论                                          | 证据                                                                      |
| ------------------------------------------- | ----------------------------------------------------------------------- |
| `WS_EX_NOACTIVATE` 能写进去，且 **WinUI 不会把它改回去** | 外部读到的扩展样式含第 27 位（`0x08000000`），多次读数一致                                   |
| 无边框 + NOACTIVATE 的窗口**能正常渲染**               | 面板内容随点击实时更新                                                             |
| NOACTIVATE 下**鼠标点击能到达窗口**                   | 真实合成点击后，面板与外部的点击计数都递增                                                   |
| 点击**不会夺走前台焦点**                              | 点击后本窗口仍未持有前台焦点                                                          |
| 全局热键在"非提权进程 + 桌面在前台"下工作正常                   | 合成 `Ctrl+Alt+J` → 收到 `WM_HOTKEY` → `IsWindowVisible` 真的在 False/True 之间切 |
| 拖动、亚克力背景、居中、退出按钮均可用                         | 逐个点过，日志里每一步都有对应记录                                                       |
| 进程无启动崩溃、无非空指针事件                             | 启动后静置数秒，无异常记录                                                           |

**因此 README 下面表里只剩"游戏里"的部分需要实测。** 已经被上面的结论覆盖掉的不是"不重要"，
而是"在本机上成立"——如果你换机器或换 Windows 版本，值得重跑一遍。

> 这条**还没**验证、也是整个 Phase 0 最可能翻车的点：**游戏捕获鼠标（`SetCapture`）时**，
> 点击还能不能到达浮窗。上面那个点击测试是在没有任何程序抢鼠标的情况下做的。

## 这次原型自己踩出来的三个坑（**都已修**，但 Phase 1 必须照做）

这三个都属于"代码看着没问题、托管属性也报正常、但实际行为是坏的"，不写日志就永远发现不了。

### 坑 1：置顶**根本没有生效**（最要命的一个）

**现象**：窗口显示出来了，却被一个普通的最大化 Chrome 窗口盖住 —— 在屏幕上看就是"浮窗自己消失了"。
按热键唤出也没用：热键只切显隐，不修样式。

**根因**：`WS_EX_TOPMOST` 这一位从来没被写进去。两条"正统"写法都不可信：

| 写法                                         | 托管属性读回 | 扩展样式里**有没有** TOPMOST |
| ------------------------------------------ | ------ | -------------------- |
| `OverlappedPresenter.IsAlwaysOnTop = true` | true   | ❌ 没有                 |
| WinUIEx 的 `WindowEx.IsAlwaysOnTop = true`  | true   | ❌ 没有                 |

而且窗口**显示稳定之前**（大约头 1 秒内），连直接调 `SetWindowPos(HWND_TOPMOST)` 都会被抹掉 ——
调用**返回成功**（`返回=0x1 错误码=0`）而样式位不在。同一个调用在窗口稳定之后再执行就成功且长期保持。
（用外部探针在已稳定的窗口上试，一次就成功：`0x08000100 → 0x08000108`。）

**现在的做法**（`OverlayWindowStyles.SetTopMost` + 每秒自愈）：

1. 判断置顶一律以**扩展样式**为准，不信任何托管属性；
2. 每秒校验，缺了就用 `SetWindowPos` 补回来；只在**确实想要**置顶时补，
   否则「切换置顶」按钮的对比测试会被自愈立刻推翻。

**Phase 1 要照做**：正式实现里也必须"以扩展样式为准 + 定期自愈"，不能只在构造时设一次。

### 坑 2：点按钮时点击计数不涨（会把结论带偏）

**现象**：点窗口里任何按钮，面板上的"点击计数"纹丝不动。而计数正是"鼠标输入有没有到达窗口"的
唯一证据，太容易被误读成"NOACTIVATE 把鼠标输入挡掉了" —— 结论会完全反过来。

**根因**：`Button` 自己会处理 `PointerPressed` 并标记为已处理，XAML 上的 `PointerPressed="..."`
订阅**收不到**这类事件（实测连点 8 次按钮，计数一直是 0）。

**修法**：在构造函数里用 `AddHandler(UIElement.PointerPressedEvent, ..., handledEventsToo: true)` 订阅。

### 坑 3：`Ctrl + Alt + M` 被别的程序占着，热键其实没注册上

**现象**：按 `Ctrl+Alt+M` 毫无反应。原因是 `RegisterHotKey` 返回"热键已注册"——
系统的组合键是**独占**的，被占用就注册不上 —— 而失败只在面板上写一行小字，很容易被忽略。

**修法**：候选列表按顺序尝试，注册第一个可用的，界面上明确写出**实际生效**的是哪个组合键。
本机实测 `Ctrl + Alt + M` 被占，自动改用了 `Ctrl + Alt + J`。

## 面板上每一项怎么看

- **存活检查（每秒跳动的时间）** —— 时间停住说明窗口卡死或没在渲染，那 `WS_EX_NOACTIVATE` 这条路有问题。

- **点击计数** —— 点窗口里**任意位置**都应该涨。点不涨 = 点击没到达窗口（问题 2 的答案）。

- **扩展样式 `0x…`** —— 是**实时回读**的，不是我以为设了什么。现在只要看两个位：
  
  - `0x08000000`（第 27 位）= `WS_EX_NOACTIVATE`
  - `0x00000008`（第 4 位）= `WS_EX_TOPMOST`
  
  正常值长这样：`0x08000108`（两个都在）。**少了 `0x8` 就是没置顶**，窗口会被普通窗口盖住。
  后面两行各自写了实际已设置 ✓ / ✗，以那两行为准，别信托管属性。

- **置顶** —— 读的就是扩展样式里那一位。见坑 1：托管属性会在样式里根本没有这一位时照样说已启用。

- **前台焦点** —— 这是问题 3 的直接证据：
  
  - 「不在本窗口 ← 游戏仍在最前」= NOACTIVATE 生效，**期望结果**
  - 「本窗口持有 ← 抢走了焦点」= NOACTIVATE 没生效，点「切换不激活」可以 A/B 对比

- **热键** —— 显示**实际生效**的那个组合键。注册失败会把系统给的原因原样显示出来。

**热键：优先 `Ctrl + Alt + M`**，按一次隐藏、再按一次显示。本机 `Ctrl+Alt+M` 已被别的程序占用，
会自动退到候选列表里的下一个（本机实测落在 `Ctrl + Alt + J` / `Ctrl + Alt + K`，取决于当时谁占着那一组合键），
面板「热键」那一行显示的就是**实际生效**的组合 —— 以它为准，别按文档里写的键。
换候选键改 `MainWindow.xaml.cs` 顶部的 `HotkeyCandidates` 数组（按顺序尝试，第一个可用的胜出）。

## 实测记录表（请把结果填在这里）

测试前提：先启动 `OverlaySpike.exe`（浮窗会出现在屏幕中央），再启动鸣潮进入游戏。

### 问题 1 / 2 / 3：可见性与可点击性

| 游戏显示模式 | 鼠标状态               | 浮窗可见？ | 点击被计数了吗？ | 点完游戏掉全屏/最小化？ | 点完前台焦点在哪？       |
| ------ | ------------------ | ----- | -------- | ------------ | --------------- |
| 独占全屏   | 3D 视角（鼠标被锁）        | 可见    | 计数了      | 点游戏还是全屏      | 点游戏没有计数，应该焦点在游戏 |
| 独占全屏   | ESC 菜单 / 背包（鼠标已解锁） | 可见    | 计数了      | 点游戏还是全屏      | 点游戏没有计数，应该焦点在游戏 |
| 无边框窗口  | 3D 视角（鼠标被锁）        | 可见    | 计数了      | 点游戏还是窗口模式    | 点游戏没有计数，应该焦点在游戏 |
| 无边框窗口  | ESC 菜单 / 背包（鼠标已解锁） | 可见    | 计数了      | 点游戏还是窗口模式    | 点游戏没有计数，应该焦点在游戏 |

> 「鼠标被锁」怎么判断：转动视角时鼠标指针不可见、光标固定在屏幕内。

### 问题 4：提权游戏前台时热键是否有效

| 场景             | 按 Ctrl+Alt+M 有反应吗？ |
| -------------- | ------------------ |
| 游戏在 3D 视角、占着前台 | 没反应，ctrl alt k可以   |
| 游戏在菜单界面、占着前台   | 没反应，ctrl alt k可以   |
| 切回桌面（游戏不在前台）   | 没反应，ctrl alt k可以   |

**结论**：`Ctrl+Alt+M` 被本机别的程序占用（组合键是**独占**的，注册不上就是彻底没反应），
候选列表顶上来的组合键在**提权游戏 + 独占全屏 + 占着前台**时照样有效 —— 三个场景全通过。
⇒ 「非提权进程用全局热键驱动浮窗盖在提权游戏上」这条路成立。

| 检查项                                     | 结果  |
| --------------------------------------- | --- |
| 「切换背景」开亚克力后，窗口是否仍然可见、内容是否仍正常渲染？         | 是   |

## Phase 0 判定：Go —— 方案 A 成立（2026-09-22 实测）

四个问题全部通过：四行场景都「可见 + 可点击」，热键在提权游戏占前台时有效，点完不掉全屏、不夺焦点。

- **独占全屏下就能用**，连游戏锁着鼠标的 3D 视角也一样 —— 不必退回「无边框窗口」，
  产品里也就不需要加"请切成窗口模式"的引导。
- `WS_EX_NOACTIVATE` 在实机成立：点浮窗既没把游戏挤出全屏，也没抢走它的前台焦点。
- 唯一与预期不同的是热键被占用这件事 ⇒ **Phase 1 的热键必须让用户可改**，不能写死一个组合键，
  否则用户遇到本机这种情况只会以为功能坏了。

**Phase 1 必须带上的两件事**（详见上面「三个坑」）：

1. 「以扩展样式为准 + 定期自愈」地维护置顶，不能只在构造时设一次；
2. `src/Elevator/Program.cs:167` 把刷新目标写死成 `Process.GetProcessesByName("GenshinImpact")`，
   鸣潮下必然找不到进程 —— 而「点一下勾选立刻 F10 刷新」正是这个功能的核心动作，
   不改这一处，浮窗勾得再顺手也刷新不了。

## 结论怎么用

- **至少一行「可见 + 可点击」** → 方案 A 成立，可以进入 Phase 1。
- **只有"无边框窗口"那两行通过** → 方案 A 仍成立，但产品里要加引导：
  检测到游戏是独占全屏时提示"切到无边框窗口模式才能用浮窗"。
- **全都不可见** → 方案 A 作废，回到技术选型（注入式 overlay 或放弃），需重新走一轮需求。
- **可见但始终不可点击** → 交互方式要重设计（比如浮窗退化为纯状态显示，用全局热键做"上一个/下一个 Mod"），
  同样需要重新确认需求。

## 已知的取舍（别当成 bug）

- **不做透明 / 穿透**：默认是不透明深色面板，方便肉眼确认"看得见"这件事本身。亚克力是额外一个开关。
- **不做 Mod 列表、缩略图、搜索**：那是 Phase 1，这个原型只验窗口行为。
- **样式设置失败是静默的**：`SetWindowLongPtr` / `RegisterHotKey` 这类 win32 调用失败不会抛异常。
  所以面板上所有状态都是**回读**显示的，请以面板为准，不要以"代码里调了 API"为准。

## 日志：窗口"自己消失"时看这里

**这版有日志文件了**，和窗口面板同时输出，写在 exe 旁边：

```
src/OverlaySpike/bin/x64/Debug/net9.0-windows10.0.22621.0/spike.log
```

每次启动都会覆盖重写，所以它**只记录最近一次运行**。

> 为什么补这个：第一版刻意"不落盘、诊断信息全显示在面板上"，理由是免得为了看日志切出游戏。
> 这个取舍是错的 —— 窗口一旦自己消失、进程一旦退出，屏幕上那块面板就什么都看不到了，
> 等于**在最需要证据的那一刻把证据丢了**。现在每次点击/每个按钮/热键触发/显隐切换都会落盘。

日志里能直接读出三种长得一样、但原因完全不同的"窗口消失"：

| 日志末尾长什么样                                 | 真实原因               | 怎么办                      |
| ---------------------------------------- | ------------------ | ------------------------ |
| `按钮: 退出 …` → `窗口 Closed 事件` → `进程正在退出`   | 点到了「退出」按钮，进程真的结束了  | 重开 exe。热键此时不可能有反应（进程都没了） |
| `按钮: 切换置顶 -> 不置顶…`                       | 窗口掉到别的窗口后面了，看起来像消失 | 再点一次热键切显隐，或点「切换置顶」切回来    |
| `切换显隐: 请求=隐藏 系统实际 IsWindowVisible=False` | 热键正常，是**你自己**按的    | 再按一次热键即显示                |
| `!!! 未处理异常`                              | 崩了，下面的堆栈就是原因       | 把日志发我                    |

若日志最后一行是 `已 Activate，进入消息循环` 而没有后续任何交互记录，
说明"消失"发生在**进程之外**（例如被任务管理器结束、或被别的东西盖住）。·
