# Product Requirements Document: 拖拽通道兼容改造（关掉 UAC 的机器）

**Version**: 1.0
**Date**: 2026-10-09
**Author**: Sarah (Product Owner)
**Quality Score**: 91/100

---

## Executive Summary

在关掉 UAC 的机器上（`EnableLUA=0`，网吧无盘机最常见），JASM 的拖拽安装**从第一天起就是死的** —— 不是版本回归，是环境命中了一个平台缺陷：全员提权时，WinUI 3 收不到来自外部程序的拖放（`DragEnter` 根本不触发，光标显示禁止符）。

更糟的是 JASM 的两个既有机制让这个坑**必然被踩中**：一是启动时的「与 shell 同级」降权策略看到 shell 是高完整性就**主动保持高**，正好落进缺陷的触发条件；二是自检会把这种情形**误判**成「拖拽投递被第三方软件接管」，建议用户去查网维/无盘软件 —— 把用户引向一个根本不存在的病因。

本需求要让拖拽安装在这类机器上真正可用，验收以**那台关 UAC 的真机**为准：概览页与浮窗两个主路径都能拖入成功，且**光标显示为可放置**（不是「文件能落进来但一路禁止符」）。

## Problem Statement

### Current Situation

一次完整的现场排查（2026-10-09，报障用户机器）得到的事实：

- 自检报告：`本进程 高(0x3000)`、`资源管理器 高(0x3000)` → **同级**；`拖拽事件：10 秒内一次都没收到`。
- 用户描述：**从来没有**能拖进去过 —— 不是某次更新后坏的。
- 同一环境下，**WPF / WinForms 的拖放正常**，只有 WinUI 3 / Avalonia 这类新框架收不到（Avalonia 讨论 #16544）。
- 框架自己给出的错误原文：`Drag start failed. If this is an elevated process, drag/drop is currently not supported there`（WindowsAppSDK #3921）。
- 该缺陷自 WASDK 1.4 存在，到 1.7 仍未修（WindowsAppSDK #4433）→ **降级 WASDK 是死路**。

结论：**不是整机封杀拖放，也不是网维软件，是 WinUI 3 宿主 OLE 落点（`IDropTarget`）的方式在全员提权环境下失效。**

### Proposed Solution

绕开 WinUI 3 的拖放实现，**在 JASM 进程内自建一个纯 Win32 落点窗**（非 WinUI，自己实现 `IDropTarget`），由它承接拖放、拿到正确的系统光标反馈，再把文件路径交回现有的落点判据。仅在环境判据命中（UAC 关闭）时挂载，正常机器一行代码路径都不进。

### Business Impact

- **恢复一类用户的核心功能**：网吧/无盘机用户目前完全无法拖拽安装，只能靠「添加 Mod」按钮绕行。
- **终止一轮误诊循环**：此前为这个问题投入的降权、换份、探针、自检等修复，方向都指向「权限不等」和「第三方接管」，与本因无关。本需求同时修正自检结论，避免后续继续误诊。
- **降低支持成本**：自检报告从「让用户去查网维」变成「这台机器命中已知缺陷，等修复」，用户的下一步动作明确。

## User Personas

### Primary: 网吧/无盘机用户

- **Role**: 在网吧或使用无盘系统的机器上玩原神/鸣潮，用 JASM 装 Mod
- **Goals**: 把下载好的 Mod 包拖进 JASM 直接装，跟在家里一样
- **Pain Points**: 拖进去毫无反应、光标一路禁止符；不知道是自己操作错了、Mod 有问题，还是软件坏了
- **Technical Level**: 初级到中级 —— 不会去翻注册表或组策略，也不该被要求去改 UAC
- **环境特征**: UAC 关闭（全员提权）、可能装有网维/无盘管理软件、可能不允许改系统设置

### Secondary: 普通家用机用户

- **Role**: UAC 正常开着的个人机用户（当前绝大多数用户）
- **Goals**: 什么都不变，拖拽照旧能用
- **Pain Points**: **本次改造如果误伤他们**，会把一个可用功能弄坏 —— 这是本需求最大的回归面
- **Technical Level**: 不限

## User Stories & Acceptance Criteria

### Story 1: 网吧用户拖 Mod 包进概览页

**As a** 网吧机用户
**I want to** 把 Mod 包拖进 JASM 概览页
**So that** 我能像在别的机器上一样直接安装

**Acceptance Criteria:**
- [ ] 拖拽过程中，光标显示为**可放置**（不是禁止符）
- [ ] 松手后 ≤200ms 内开始处理，并进入现有安装流程（角色识别、安装）
- [ ] 判据与现有一致：该拒的仍然拒（拒绝时的表现与原落点相同）

### Story 2: 网吧用户拖文件进浮窗

**As a** 网吧机用户
**I want to** 把 Mod 文件拖进游戏内浮窗
**So that** 我不用退回主窗口

**Acceptance Criteria:**
- [ ] 光标显示为可放置
- [ ] 松手后 ≤200ms 内开始处理
- [ ] **浮窗只收真文件**的既有判据不变（网盘客户端/压缩软件给的虚拟文件仍然不算）
- [ ] 浮窗原有的唤起、拖动、键盘操作行为不受影响

### Story 3: 普通用户完全无感

**As a** UAC 正常开着的用户
**I want to** 拖拽行为跟以前一模一样
**So that** 我不用重新学、也不会遇到新问题

**Acceptance Criteria:**
- [ ] 环境判据不命中时，新落点窗**不被创建**，不进任何新代码路径
- [ ] 现有四个落点的手测配方全部通过
- [ ] 无新增可见窗口、无闪屏、无焦点变化

### Story 4: 用户点自检拿到真因

**As a** 拖不进去的用户
**I want to** 点一下自检就知道到底哪里不对
**So that** 我知道该做什么，而不是去查一个我没装的东西

**Acceptance Criteria:**
- [ ] 在关 UAC 的机器上，结论指向「这台机器 UAC 关闭，WinUI 3 收不到拖放」，不再是无据的「被第三方软件接管」
- [ ] 扫到已知接管拖放的进程名单时，**仍然**点名（这条线索本身有效，不能一并删掉）
- [ ] 报告给出明确的下一步（等待修复 / 使用添加按钮）

## Functional Requirements

### Core Features

**F1: 环境判据（决定是否挂载新落点窗）**

- Description: 启动时判定本机是否处于「WinUI 3 拖放必然失效」的环境。
- 判据: **UAC 关闭**（`EnableLUA`）与/或 **shell（explorer）为高完整性** —— 二者在本缺陷上是同一件事的两个观测面，实现时以稳定性高者为准。
- 为什么必须是启动时判定: **拖拽事件收不到 = 没有任何「没生效」的信号可用于热切换**。用户拖一下没反应，JASM 这边是零事件，无法据此触发切换。因此「按需启用」只能靠环境判据在启动时决定。
- 边界: 读不到判据（权限/API 失败）时，**按不命中处理**（宁可不启用，也不要误伤正常机器）。
- 复现性: 该判定必须同时写进启动日志（沿用现有的 `启动完整性：…` 那类日志行），便于用户交日志时一眼确认走了哪条通道。

**F2: 进程内 Win32 落点窗**

- Description: 在 JASM 进程内创建一个**非 WinUI 的纯 Win32 窗口**，自己实现 `IDropTarget`（或等价的老式落点机制），由它承接外部拖放。
- 依据: 同环境下 WPF/WinForms 的拖放正常，而只有新框架坏 —— 说明系统层面没有禁止，**换一个非 WinUI 的落点宿主就能收**。
- 关键要求: **光标必须是正确的**。这是本需求的验收项之一，也是判断方案是否成立的主要信号。
- 约束: 不新增可分发产物（不新建 exe）；窗口必须在 UI 线程创建；不得抢焦点、不得遮挡或吞掉现有 XAML 的鼠标交互。
- 失败处理: 窗口创建失败时不得影响 JASM 其余功能，记录日志并退回现状（拖拽不可用，但按钮可用）。

**F3: 事件路由到现有落点判据**

- Description: 新通道拿到文件路径后，**完全沿用**原落点的判据与流程，不新增一套业务逻辑。
- User flow: 新窗口收到 Drop → 取出文件路径 → 交给对应落点（概览页 / 浮窗）的现有处理入口 → 后续行为与现在的拖拽完全一致。
- Edge cases:
  - 拖入的内容取不到真实路径（网盘/压缩软件的虚拟文件）→ 按原落点判据拒绝，表现与原版一致。
  - 拖入多个文件 → 按原落点判据处理（该拒就拒）。
  - 拖到落点窗覆盖范围之外 → 不产生任何行为。

**F4: 自检文案与判据修正**

- Description: 修正自检结论的**无据断言**。当前 `BlockedByMachineChannel` 一档的结论与出路是写死的「被第三方软件接管」，即使一个可疑进程都没扫到也照样这么写。
- 修正要点:
  - 扫到已知名单才敢说「第三方接管」；
  - 没扫到、且命中 UAC 关闭这一档时，说明是**本机 UAC 关闭导致 WinUI 3 收不到拖放**，并给出「等待修复 / 先用添加按钮」的下一步；
  - 已知名单本身**保留**（它是有效线索）。
- 关联: 这一段与 F1 共用同一套判据，实现上应只有一份判定来源，避免「自检说 A、开关按 B 走」的分裂。

### Out of Scope

- **详情页与设置页自检框**两个落点的适配（本 MVP 只做概览页 + 浮窗，见分期）
- **独立落点助手进程 + IPC** 形态（列为二期兜底，见 F2 的失败处理）
- 触摸、笔、键盘发起的拖放（现状也只覆盖鼠标文件拖放）
- 修改用户机器的 UAC 设置、或降级 Windows App SDK（前者网吧不允许，后者已验证是死路）
- 任何新增第三方依赖

## Technical Constraints

### Performance

- 松手 → 开始处理 ≤ **200ms**（不含安装耗时）。大文件与多文件不得卡 UI 线程。
- 新落点窗在非拖拽期间必须零开销（不轮询、不占 CPU）。

### Security

- **不得削弱现有的提权/降权模型**：本需求不改变 JASM 与 shell 的完整性级别策略，只换拖放投递的通道。
- **不得引入基于 UIPI 的绕过手段**（如放开 `WM_DROPFILES` 之类消息的过滤器）作为默认路径 —— 那类做法在别的配置下会带来攻击面，且已知在本场景无效（两边同为高完整性，UIPI 根本不是拦路者）。
- 新窗口只接受拖放，不承载任何业务逻辑，作为攻击面应尽可能薄。

### Integration

- **现有拖放落点**：概览页、浮窗（本 MVP）；详情页、自检框（二期）
- **完整性检测**：复用现有 `AppElevation` / `WindowProcessQuery` 的能力，不另起一套
- **自检**：与 F1 共用判据来源
- **Win32 interop**：沿用项目既有做法（调用新的 Win32 API 时须在对应工程的 `NativeMethods.txt` 中登记函数名，否则会被 XamlCompiler 的错误盖住）
- **线程**：新窗口必须在 UI 线程创建（非 UI 线程创建 WinUI 相关窗口会导致进程被静默打挂）

### Technology Stack

- .NET 9 + Windows App SDK 1.7（**不升级、不降级**）
- 允许使用 BCL 与 Win32 interop；不新增 NuGet 依赖
- 需兼容：Windows 10/11 全系，重点覆盖 Windows 11 24H2 及以后（关 UAC 的配置）

## MVP Scope & Phasing

### Phase 0: 探针（必须先做，未完成不进入 Phase 1）

- 在 JASM 内加**最小可撤**的代码：给窗口设上落点相关样式与消息处理，**只记录不处理** —— 记录外部拖放的消息/事件到底到不到、光标表现如何。
- 目的: 本机（开发机，UAC 开着、三个进程全中完整性）**无法复现**此缺陷，唯一能回答这个问题的是那台真机。
- 退出条件: 拿到真机结论，确认进程内方案在**光标**这一项上成立。不成立则直接跳 Phase 2 的兜底形态。

### Phase 1: MVP

- F1 环境判据 + 启动日志
- F2 进程内 Win32 落点窗（概览页 + 浮窗两个落点）
- F3 事件路由，判据完全沿用
- F4 自检文案与判据修正
- 200ms 响应指标

**MVP Definition**: 在那台关 UAC 的机器上，概览页与浮窗都能拖入成功且光标正确；同时开发机上四个落点零回归。两者都满足才算交付。

### Phase 2: Enhancements（Post-Launch）

- 详情页与设置页自检框两个落点适配
- **独立落点助手进程 + IPC** —— 若 Phase 0 或 Phase 1 证明进程内形态拿不到正确光标，则以此形态重做落点部分
- 自检报告进一步细分档位（按判据来源给出不同措辞）

### Future Considerations

- 把「本机拖放是否可用」做成一次性自检项，开机即给出结论（减少用户先撞墙再自检）
- 关注 WindowsAppSDK 上游是否修复（#3921 / #4433）—— 若修复，本机制可整体下线，回到原生实现

## Dependencies & Blockers

**Dependencies:**

- **一台关 UAC（`EnableLUA=0`）的真机** —— 用于 Phase 0 探针与最终验收。报障用户那台机器即为候选，但需要用户配合，属于外部依赖。
- 现有自检与完整性检测能力（`AppElevation`、`WindowProcessQuery`、`DragDropSelfCheck`）—— 已就绪。

**Known Blockers:**

- **探针结果未知**：`WM_DROPFILES` 等老式落点机制在「全员提权 + WinUI 3 进程」中能否拿到**正确光标**，目前没有直接证据。文献中唯一同型案例（C++/WinRT WinUI3 拖外部文件）报告的是「文件能落下、但光标仍是禁止符」—— 这**不满足**本需求的验收标准，因此不能据此认为方案成立。
- **本机不可复现**：开发机三个进程均为中完整性、UAC 开启，构造不出触发条件。任何「本机跑通了」的结论都不构成证据。

## Appendix

### Glossary

- **UAC / `EnableLUA`**: 用户账户控制。`EnableLUA=0` 即 UAC 关闭，此时所有进程以高完整性运行（网吧/无盘机常见配置）。
- **完整性级别 / IL**: 进程的强制完整性控制等级。高(0x3000) 表示提权运行。
- **UIPI**: 用户界面特权隔离，阻止低完整性进程向高完整性进程发送窗口消息。
- **`IDropTarget`**: OLE 拖放的落点接口。WinUI 3 在提权环境下的宿主方式存在缺陷，无法正常接收外部拖放。
- **`WM_DROPFILES` / `WS_EX_ACCEPTFILES`**: 老式（非 OLE）的文件拖放通道，由 shell 在落点带 `WS_EX_ACCEPTFILES` 时投递。
- **沙箱内已确认的事实**: 自检报告中的「同级」指 JASM 与 shell 的完整性级别相同 —— 在本缺陷里，**「同级且都为高」恰恰是触发条件**，而不是「权限没问题」。
